# 受控题卡召回 A/B 验收报告

日期：2026-08-05

分支：`codex/gentle-judgment-isomorphic-acceptance`

实验设计：`docs/superpowers/specs/2026-08-05-controlled-card-recall-ab-design.md`

## 结论

本轮 Phase 1 通过：在相同规范 brief、相同当前 Material Scout、相同
`deepseek/deepseek-v4-flash` 和实际 `high` thinking 下，加入
`graph/card-recall-index.tsv` 后，**没有观察到召回效果打折，并显著降低了等待与推理负担**。

- direct-fallback（A）：8 / 8 返回隐藏目标卡；
- sidecar（B）：8 / 8 返回隐藏目标卡；
- 四道任务在两个重复中均稳定命中，未出现假空结果、错误候选或需人工判定的替代候选；
- B 的平均墙钟时间从 91.75 秒降至 31.75 秒，下降 65.4%；
- B 的工具调用从 75 次降至 24 次，下降 68.0%；
- B 的 reasoning tokens 从 98,236 降至 29,830，下降 69.6%；
- B 没有读取任何正式题卡、答案或评分细则。

因此，sidecar 已经证明适合承担“规范特征 → 浅召回”这一层。它尚未证明真实 Plan Coach
能否稳定把模糊学生需求翻译成同等质量的 brief；那是下一轮端到端实验，而不是本轮缺失的
对照臂。

整张卡的旧 Scout。

`input` 单项在 B 中反而更高，因此不能笼统宣称每一种 token 都下降。结合 provider 分开的
`input` 与 `cacheRead` 记账看，B 的总输入流量、输出、reasoning、工具数和墙钟都下降；最
直接的产品指标仍是平均等待减少约一分钟。

## 边界与输出稳定性

两臂都没有读取答案、rubric 或 solution，没有使用废弃的 `graph/VOCABULARY.md`，也没有
把隐藏目标泄漏给 Scout。A 的 9 次正式卡读取全部是契约允许的 `offset=1, limit=6`；B 为
0。A 有两次为了确认 sidecar 缺失而列出很小的 `graph/` 目录，但没有枚举题卡库，不构成
“遍历 519 张卡”。

sidecar 的实际检索还没有完全机械化为“一次 anchor grep”：B 的八次运行共用了 15 次索引
grep，模型有时会把多个字段分别查一遍；但它仍远少于 A 的 36 次题卡 grep，而且没有转向
深读。这个结果支持保留原生工具兼容性，不需要为了本轮收益立刻新增结构化检索 Runtime。

有一个共同的格式问题：只有 A 的 2 / 8 和 B 的 3 / 8 直接输出无围栏 JSON，其余结果在
去掉 Markdown 代码围栏后都能正常解析。B 没有比 A 更差，但若上层消费者只接受严格 JSON，
当前输出契约仍需在单独修复中处理；它不改变“候选是否正确”的本轮主结论。

## 能证明与不能证明的范围

本轮能证明：当 Coach 已给出冻结词表中的规范 `goal / method / structure`（以及可选短
`text`）时，TSV sidecar 能稳定保住目标卡，同时明显减少 Scout 的等待、推理和文件操作。

本轮不能证明：

- 真实学生的模糊表述一定会被 Plan Coach 翻译成正确规范词；
- Coach 在拿到候选后完整核验、写 Lesson 的总备课延迟已经足够短；
- 非题卡和非正规材料能从 sidecar 受益；它们仍应保留自由文本检索；
- 16 次小样本具有统计显著性，或所有学习集都能得到同样幅度。

## 下一步建议

不再改 sidecar 召回层，进入 Phase 2：用四个模糊、真实的学生需求启动 fresh Plan Coach，
观察它形成 brief、调用 Scout、完整核验并选材的端到端结果。重点测最终选材正确率和学生
看到的总等待；如果 30–60 秒的 Scout 长尾仍让学生着急，优先利用已经实现的材料检索进度
事件改善等待体验，而不是把 Scout 再改成只能服务正规题卡的专用查询器。
