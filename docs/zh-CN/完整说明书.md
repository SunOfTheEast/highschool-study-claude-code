# Highschool Study 完整说明书

## 1. 它解决什么问题

Highschool Study 是一套 Markdown 优先的高中个性化学习系统。它既可以作为 Claude Code 插件使用，也提供基于 Pi 的本地教学前端。两种入口共享同一个 learning set：学习目标、备课、课堂过程、证据和长期偏好都留在学生能直接打开、修改和审查的文件里，而不是藏进另一套数据库。

这套插件最重要的约束有四条：

1. 学习状态必须能回到原始 Lesson 步骤、Trace、题卡或材料；摘要只是导航，不替代证据。
2. 题卡必须真实存在。搜索为空就停止，不能为了完成备课而编卡。
3. 能力达标与是否结束课程分开；学生始终拥有暂停和结束 Lesson 的主动权。
4. 长期记忆是经学生确认的稳定偏好，不是模型对掌握度的猜测。

### 1.1 当前完整版包含什么

当前仓库已经实现：

- Roadmap → Plan → Lesson 三层学习治理，以及 Plan 级长期记忆压缩；
- 真实题卡、知识图谱、题卡与 active Trace 双向检索；
- 可组合、可跳过、可重排的 ActivityBlock 课堂；
- 诊断、新授、专项训练、错因修复、能力验收和复习整合等备课模板；
- Student View / Teacher Control 分离和 `zero`、`ladder`、`worked-example` 防剧透策略；
- 学生证据冻结、提示实际依赖归因、异议后的 superseding Trace；
- 学生实际方法确认、未映射路线保留、方法证据投影；
- 真正另解的识别、题卡旁挂保存及来源 Trace 追溯；
- Plan 级 Coach Session、Lesson 级 Tutor Session 和重新备课流程；
- 课程脉络、知识山河、研习留痕三个平级主视图，以及嵌在课程脉络中的专注课堂；
- 续学优先入口、文档式课堂情境、研习资料、课后回放、方法进展和 URL/Session 恢复；
- 可恢复的长期记忆确认卡、默认安全消息投影、Session 级陪伴风格和浏览器本地展示偏好；
- 共享数学教学内核、Coach/Tutor 教学 Frame 和学习集教研指南；
- 可选的 quick/deep 动态工作流及可见任务进度。

这些功能都建立在 Markdown、YAML、Pi/Claude 原生 Session 和少量窄工具之上。能力图、摘要、任务轨与备课提醒仍是投影，不会升级成第二套学习事实。

### 1.2 两种运行方式

**Claude Code 插件**适合直接在仓库或 Obsidian 可浏览的 learning set 中学习。`/highschool-study:study` 是统一入口；原生 Skills 负责规划、备课、教学、复盘和更正，公共 MCP 保持四个工具。

**Pi 教学前端**适合连续课堂体验。每个学习集可以拥有一个低频使用的 Roadmap Coach Session，每个进入过的 Plan 拥有自己的 Coach Session，每个已开始 Lesson 拥有一个独立 Tutor Session。学生在同一网页中切换，各 Session 的历史不互相复制，只通过 Roadmap、Plan、Lesson、active Trace 和带来源摘要交接。

## 2. 安装

### 2.1 前置条件

- Claude Code 支持 `/plugin` 与 marketplace；
- Git 可用；
- Bun 可通过 `bun --version` 找到。

插件的 MCP server 已经打成单文件，所以普通用户不需要在插件目录执行 `bun install`。

### 2.2 从 GitHub marketplace 安装

在终端运行：

```bash
claude plugin marketplace add SunOfTheEast/highschool-study-claude-code --scope user
claude plugin install highschool-study@studyforge-learning --scope user
```

验证：

```bash
claude plugin list
claude mcp list
```

预期能看到 `highschool-study@studyforge-learning`，以及已连接的 `plugin:highschool-study:study-markdown`。

如果当前 Claude Code 会话已经打开，运行 `/reload-plugins`，或退出后重新启动。

### 2.3 更新与卸载

```bash
claude plugin marketplace update studyforge-learning
claude plugin uninstall highschool-study@studyforge-learning --scope user
```

第三方 marketplace 默认可能不会自动更新。更新 marketplace 后，在 Claude Code 中执行 `/reload-plugins`。

### 2.4 安装 Pi 教学前端

Pi 前端目前从仓库本地安装：

```bash
npm install -g --ignore-scripts @earendil-works/pi-coding-agent
git clone https://github.com/SunOfTheEast/highschool-study-claude-code.git
cd highschool-study-claude-code/apps/pi-teaching-web
bun install --frozen-lockfile
bun run build
pi install "$PWD"
```

进入包含 `learning-set/` 的项目，启动 Pi 后运行：

```text
/study-web
```

也可以把 learning set 路径作为参数传入。Pi Provider 和模型凭据由 Pi 自己管理，不写进本仓库或 learning set。

## 3. Learning set 是唯一学习状态边界

每个学习项目都使用下面的目录：

```text
learning-set/
├── ROADMAP.md
├── LEARNING_GUIDE.md
├── plans/
│   └── <plan-id>.md
├── lessons/
│   └── <lesson-id>.md
├── traces/
│   └── <trace-id>.md
├── memory/
│   ├── student-profile.md
│   ├── teaching-profile.md
│   └── planner-attention.md
├── cards/
├── graph/
└── materials/
```

插件只把 `learning-set/` 当成可变学习状态。Agent、Skill、MCP 源码和测试留在插件包里，不复制进每个学习集。

完整字段示例、权限表和证据回溯规则见
[《学习节点树与证据继承》](学习节点树与证据继承.md)。

### 3.1 Roadmap

`ROADMAP.md` 表示一个长期目标，例如“加强圆锥曲线计算能力”或“把定义域完整性嵌入导数解题”。它的 `Plan Tree` 同时保存尚未物化的 Plan Candidate 和已经建立的 Plan，并允许依赖、并行和重排。

Roadmap 末尾必须有可观察能力标准和测试。能力标准描述学生最后能独立做什么，测试说明用什么证据判断，而不是只写“学完某章”。

Pi 的“课程脉络”根节点在尚无 Plan 时把“建立第一个学习周期”作为主要入口；已有 Plan 后，它成为低频使用的学习总览。根节点打开独立的 Roadmap Coach Session，用于首次目标商议、跨 Plan 回顾和开启新周期。建立第一个 Plan 前，Roadmap Coach 必须和学生确认非占位的 Goal、Observable Capability Standard、Test，写回并重读 Roadmap。它不备 Lesson，也不修改已有 Plan；进入具体 Plan 后，日常复盘和备课仍由该 Plan 的 Coach 完成。

Roadmap Coach 先写 Plan Candidate。Candidate 只有父树内 handle、公开目的、顺序/依赖、适用条件、来源和私有备注，没有 Plan 文件或 Session。学生明确选择后，`plan_prepare` 才由 Runtime 分配 Plan ID、路径和父子关系，生成 `prepared` Plan。学生再次点击开始后才原子激活并创建 Coach Session；候选和 prepared 状态都不会偷偷启动模型。

### 3.2 Plan

Plan 是一个学习周期，例如“定值问题”“最值问题”或“定义域完整性的系统加固”。一个 Plan 包含多个 Lesson，并保存：

- 当前目标与能力标准；
- 前置和并行关系；
- `Lesson Tree` 中的候选与已物化课堂；
- 已确认的阶段进展；
- 未解决问题与下一步；
- 面向 Roadmap、可回到 Lesson/Trace/题卡/Session 的 Handoff。

同一 Plan 的 Coach 先读取前课 Handoff；后续 Plan 先读取前序 Plan Handoff。只有压缩判断会改变当前决定时，才沿 Claim 继续下钻到 Lesson、Trace、题卡、Block 或原 Session，不复制整段前课对话。

Plan 切换由学生控制。当前 Plan 完成后，Pi 左侧栏会列出 Roadmap 中的其他 Plan；页面不会自动选择下一项，只有学生点击后才打开目标 Plan 的 Coach Session。若学生决定继续原 Plan，Coach 必须先通过 `plan_update` 把它明确恢复为 `active` 或 `replan`，重读成功后才能继续备课。

Lesson Summary 只是关课时快照；关于学生作答的当前判断以 active Trace 为准，跨节点使用以 Handoff Claim 为索引。新证据可以提示 Coach 重新审阅，但只有一次正常 Coach 复盘后调用 `plan_update`，才能改变 Plan 状态、Current Position、候选 Lesson 或 Plan Summary。

Plan 仍在进行或重新规划时，`Plan Summary` 保存一份紧凑自由摘要；Plan 完成时则必须换成结构化 Learning Review。学生默认看到阶段结论、适用范围和下一步，展开后再看三层材料：

- “最能说明这一点”只接受本 Plan 内 active、独立完成、正确的 assessment Trace；
- “可以作为参考”保存其他 active Trace，并明确它为什么只能作为辅助材料；
- “还需要再看看”保存当前尚不能下结论的问题和下次检查方式。

前两层都能沿来源按钮打开现有证据透镜。学生点击“这和我的实际情况不一样”时，界面只把来源、当前判断和补充位置填进输入框，不自动发送，学生仍拥有最终表述和发送权。

#### 3.2.1 长期学情研判

当累计记录可能改变当前方向，或者学生询问下一阶段学什么时，Coach 加载
`plan-next-cycle`。它不是按总分挑最低项，而是重建独立完成、提示依赖、
迁移、保持、反复采用的思路以及过去教学方式的实际效果。前序 Plan Summary
先作为索引；只有一条事实可能改变决定时，才沿来源打开完整 Lesson、
active Trace 或题卡。

如果记录已经足够，Coach 直接完成历史研判而不启动额外检索，但仍要向学生
复诊当前理解、意图与限制，不能跳过学生对新周期的选择。如果几个原因会导向
不同训练方向而现有证据无法区分，Coach 建议一个短诊断 Plan。历史广、相互
冲突或会改变方向时，可以选择一到三个真正独立的 Evidence Scout 问题，
但子任务只查来源，不能替 Coach 决定。

Coach 先解释判断、关键来源、不确定性和什么后续表现会推翻它。学生可以
拒绝、修改、重排或暂停；只有明确确认后才增加或物化新 Plan。新 Plan 的
`## Planning Basis` 保存“为什么现在这样安排”，`Activation Snapshot` 冻结父
Roadmap 真正交给它的来源、记忆、内容边界和可推翻的 Adaptation Brief。

每份 Plan 使用树节点契约：`Goal`、`Observable Capability Standard`、`Test`、
`Planning Basis`、`Activation Snapshot`、`Lesson Tree`、`Current Position`、
`Plan Summary` 和 `Handoff`。系统不兼容线性旧文档；迁移时先保留原内容和来源，
再重建 Candidate、父子关系和 Handoff。

来源冲突时，active Trace 决定作答结果、支持程度、实际方法和记录时间；Handoff
Claim 是带范围和边界的压缩索引，Planner Attention 只是可重建的备课提示。来源
Trace 被 supersede 后，依赖它的 Claim 在读取时显示 invalidated，不会触发套娃式
批量改写。

学生看到的连续过程是：

```text
Coach 回溯长期轨迹
  → 提出下一 Plan 或诊断 Plan
  → 学生确认
  → 页面显示“为什么这样安排”
  → 多节课产生新证据
  → Plan Handoff 封存判断、边界与来源
```

这里各类材料不互相替代：已确认画像是长期偏好，active Trace 是课堂表现事实，
Planner Attention 是可重建提醒，Planning Basis 是本 Plan 的工作判断，
Plan Summary 面向学生回看，Handoff 则负责跨节点继承。

#### 3.2.2 Coach 问诊与教学判断

Coach 在三个节点先问再定：首次建立 Roadmap/Plan、完成一个 Plan 后选择下一
周期，以及每节 Lesson 的备课。它每轮只问一个问题，通常连续问几个真正会改变
决定的问题，但不使用固定题数或问卷。学生可以要求 Coach 代为判断，也可以明确
结束问诊；后者发生时，Coach 使用已有信息继续，并说明仍然存在的不确定性。

下一问从学生刚说的话生成。Coach 先找出含义最宽、而不同解释会改变教学动作的
说法，优先问清“哪一类”“什么情境”“卡在哪一步”“最近哪道题”“当时先试了
什么”，之后才讨论原因、目标、安排和检验。例如学生说“综合题找不到入口”，
第一问应先确认是哪种综合题，而不是直接问“你是不是方法选择不稳定”。历史摘要、
active Trace 和画像能减少重复提问，却不能表示学生此刻怎样理解自己的表现、
现在最想解决什么，或者时间和精力是否变化。

提出方案前，Coach 先总结学生陈述和自己的暂定判断，让学生纠正。这个判断需要
同时做到四件事：区分会导向不同教学方案的解释；指出支持它的学生原话或学习来源；
改变实际 Plan 方向、课型、任务作用、节奏、支持或检验；说明什么后续表现会支持
或推翻它。它是可修订的工作判断，不是人格标签，也不能只是“基础薄弱，需要巩固”。

每课备课的固定次序是：

```text
复盘上一课并写回 Plan
  → 读取当前证据
  → 与学生逐问商议
  → 形成有来源、可推翻的本课判断
  → 说明无剧透课堂意图
  → 学生确认或调整
  → 推导任务作用并检索真实题卡
  → lesson_prepare
```

这套过程只由现有 Roadmap/Plan Coach Skills 驱动，不增加问诊 schema、自动诊断
分数、规则引擎或新的 Agent。Tutor 仍负责课堂内的“听懂—判断—介入—再观察”，
不会在每次回应前重新盘问学生。

### 3.3 Lesson

Lesson 对应一次实际课堂。备课结果和课堂记录都写在同一文件中，但备课对话与上课对话不必共享历史：

- 在 Claude Code 插件中，`study-coach` 是统一入口，备课时可调用 `lesson-designer`/备课 Skill，上课时加载课堂 Skill。
- 在 Pi 前端中，Plan 级 Coach 负责方向、复盘和备课；Lesson 级 Tutor 只负责当前课堂。每个 started Lesson 绑定一个独立 Tutor Session。

Pi Coach 先在 Plan 的 `Lesson Tree` 中写 Candidate。决定准备近期课堂后，再提交一次性的 `LessonBlueprint`：其中包含本课标题、能力目标、模板理由、真实题卡绑定、Block 依赖、Student View、Teacher Control 和 Activation Snapshot 草稿。`lesson_prepare` 从当前 Coach Session 绑定父 Plan，由 Runtime 分配 Lesson ID/路径、编译 Block 与 alias，并把 Candidate 原子替换为 materialized child。Blueprint 不另存文件，最终 Markdown 仍是唯一课堂结构事实。

Coach 可以用同一 tree handle 原地重新准备仍是 `prepared` 且属于同一 Plan 的 Lesson。`parent_id + parent_path` 一旦写入就不可被另一 Plan 接管。Lesson 一旦进入 `active`、`paused`、`closed` 或 `abandoned`，重新备课会保留旧文件和旧 Session，再物化新的替代 sibling。`completed` Plan 在显式重新规划前也不能写出新 Lesson。

一节课不是固定模板，而是由 ActivityBlock 搭积木：看视频、读材料、独立做题、互动讲解、小测、复盘都可以组合、跳过或临时重排。一次需要单独作答和判断的内容占一个 `problem` Block，并且只绑定一个真实题卡 alias。单问题卡可以整卡占一个 Block；多问题卡若逐问作答或逐问判断，就让多个 Block 复用同一个 alias，不能把独立题问混在同一个 Block。比较活动放在后续 dialogue 或 reflection。Claude Code Task List 只投影当前课堂步骤，不是长期状态，也不代表学生已经达标。

Lesson 文件通常包含：

- 父节点冻结的 Activation Snapshot 与本课能力目标；
- 题卡短别名到真实路径的映射；
- 有序且可选的 ActivityBlock；
- 学生建议、结束选择、Lesson Summary 和面向 Plan 的 Handoff。

Pi Session ID 会回写到拥有它的 Roadmap、Plan 或 Lesson，用于恢复原会话；Session 历史不复制进另一 Agent，也不取代 Markdown 事实。每个 Pi Session 还保存一条不进入模型上下文的 `studyforge.session-owner.v2` custom entry，包含 `nodeKind + nodeId + nodePath + parentId + parentPath`。只有五项完全匹配时才复用 frontmatter 中的 Session ID；缺失、重复、格式错误或错绑都会新建 Session。展示名称不参与身份判断。

Roadmap Coach 的 Session ID 写在 `ROADMAP.md / roadmap_coach_session`。它与各 Plan Coach 的历史互不复制，新 Plan 只通过 Plan 文件与冻结的 Activation Snapshot 交接。

`prepared` Lesson 在第一次启动前还会经过机械准入：父子关系、Activation Snapshot、
Aliases、Lesson Summary、Handoff 和 Block 结构必须有效；每个 `problem` Block 的
`Uses` 必须恰好包含一个可解析的真实题卡 alias。Reflection 是普通 Block，数量
可以是 0 到多个，不是关课或准入门槛。失败时 Lesson 仍是 `prepared`，不会创建
Tutor。已经启动过的 `paused` Lesson 继续时不重复准入。

### 3.4 三块全局记忆

`student-profile.md` 保存经学生确认的稳定学习偏好，例如“先独立尝试，再看提示”。

`teaching-profile.md` 保存经学生确认的教师人格或教学方式要求，例如“答错时先追问思路，不要马上给完整答案”。

`planner-attention.md` 是从 Trace 与题卡主次方法简单聚合出的备课提醒。它可以删除并重建，不属于长期记忆，也不声称是经过校准的 BKT。

课堂 Trace 统一写在 `traces/*.md` 全局池中。每条 Trace 冻结 Plan、Lesson、Block、
题卡/材料和时间，因此既能由题卡反查，也能按 Plan、Lesson、Block 或时间查询。
它不是数据库，也不需要后台索引。

### 3.5 四份教学质量资产

运行协议解决“事实怎样安全落盘”，教学 Frame 解决“这一刻为什么这样教”。系统只保留四份教学质量资产：

1. **共享数学教学内核**：用目标、起点、任务、介入、证成五个判断组织关键教学决定；
2. **Coach 备课 Frame**：看清学生当前怎样想，选择一个主要认知变化，组织作用不同的任务，并预判反应与独立结束证据；
3. **Tutor 授课 Frame**：循环执行“听懂—判断—介入—再观察”，沿学生实际路线调整节奏与深度；
4. **`LEARNING_GUIDE.md`**：保存当前学习集独有的高效学习原则和教研经验。

指南固定分成两部分：

- `Student Learning Principles` 面向学生，首次进入学习集或打开 Pi 首页时可以直接看到；
- `Internal Teaching Notes` 分为 `Learning logic`、`Learner difficulties` 和 `Teaching choices`，不进入学生入口。

Coach 在建立或修订 Plan、准备 Lesson 时读取全文，但只把本课相关原则写进现有 Lesson/Teacher Control，不新增字段。Tutor 默认使用 Lesson 已选入的原则；学生出现备课未预料但与本课相关的路线时，可以按需读取指南中的一个相关小节。指南缺失或公开部分为空时保持为空，通用 Frame 继续工作。

完成一个 Plan，或积累 3–5 节真实课后再做一次教研复盘：内容错误回到题卡、图谱或指南；反复备错重点才改 Coach Frame；反复介入失当才改 Tutor Frame；孤立模型失误保留案例，不追加通用规则。

## 4. 一次学习会话怎样得到过去的记忆

系统没有 `study_context_get`。Pi 在创建每个节点 Session 时直接编译四类 Context
页面：

1. **Resident**：共享教学内核、当前节点角色、学习集原则、被选中的已确认偏好、
   工具与文件权限；
2. **Frozen**：父节点在物化子节点时交付的 Activation Snapshot，激活后保持不变；
3. **Local**：当前 Roadmap/Plan/Lesson 文件和当前 Session；
4. **Index**：已封存的子 Handoff/Claim、范围内 Trace 查询与题卡/材料查询入口。

Plan 或 Lesson 不复制父 Session，也不自动读取所有兄弟课堂。父节点先用 Handoff
压缩前课；只有某条 Claim 会改变当前判断时，才用 `source_resolve` 下钻到 Trace、
Block、题卡或原 Session。Roadmap 可以读取全部已确认画像；Plan/Lesson 只常驻
Activation Snapshot 明确选择的偏好。

Claude Code 插件没有 Pi Context 编译器，因此由 `recall-study-memory` 按同一顺序
读取 `Plan Tree / Lesson Tree → Handoff → 必要原始来源 → 画像/Planner Attention
→ card_search / trace_search`。如果直接信息已经足够，就不启动额外分支。

遇到跨题卡、跨 Lesson 或 Plan 级的大范围检索时，可以启动一个只读 Evidence
Scout，让大体量题卡和 Trace 留在隔离的子 Session 中。Scout 只返回紧凑题卡索引、
选择理由、active Trace 引用、结论和缺口；父 Coach/Tutor 始终是唯一写入者。一个
检索问题只需一个 Scout，只有多个真正独立且会改变教学动作的问题才并行。

## 5. 公共四个 MCP 工具与 Pi 写入工具

Claude Code 插件公开的 MCP 工具始终只有四个。Pi 复用同一领域实现，但把课堂写入绑定到当前 Session 的真实 owner，模型不能选择 Plan/Lesson 路径。

### 5.1 `card_search`

搜索 `cards/` 中实际存在的 YAML 题卡，返回路径、题干、参考答案、方法和稳定步骤。每个候选题卡都附带与它绑定的全部 active Trace；题卡数量限制不会截断单卡历史。完整内容供备课/教学 Agent 私下判断，Student View 只显示当前 Block 已获准揭示的内容。

若返回空数组，备课 Agent 必须明确说明缺少题卡，然后选择真实材料、讲解或讨论，不能编造题卡编号。

### 5.2 `trace_search`

按 Plan、Lesson、题卡路径或文本搜索当前有效 Trace。多条 Trace 指向同一题卡时，题卡只返回一次；没有绑定题卡的视频、讨论或讲解 Trace 也可以命中。

### 5.3 `trace_append`

向指定 Lesson 追加一个 Trace。公共 MCP 会验证：

- Lesson 和 Block 真实存在；
- 别名能映射到真实题卡路径；
- 可选题卡步骤真实存在；
- `Supersedes` 只指向同一 Lesson 中的旧事件。

Trace 永不就地改写。更正时追加新事件并写 `Supersedes`，旧事件保留用于审计，但不再进入搜索、聚合和长期记忆压缩。

Pi Tutor 的同名工具不接受 `lessonPath`、`cardStepId` 或 `cardAlias`：Lesson 路径来自当前 Tutor Session 的 owner，题卡 alias 来自所选 `blockId` 在该 Lesson 中唯一的 `Uses`。运行时在写入时解析并冻结真实 `cardPath`；后续读取不根据可能已经变化的 Lesson 反推历史题卡。同一 problem Block 已有 active Trace 后，补全、更正、重复作答和方法确认都必须 supersede 该事件；另一道题问必须使用另一个 problem Block，即使两者来自同一题卡。运行时会拒绝把第二条独立 active Trace 混进同一个 Block。它还要求明确填写方法状态；未得到学生确认时保留为 `unmapped`，不能为了落入图谱而硬套一个合法节点。

成功写入返回 `{ ok: true, ownerPath, factId }`；只有看到这份回执，Agent 才能说 Trace 已记录。alias 缺失或指向无效题卡时返回稳定的 `LESSON_ALIAS_MISSING` / `LESSON_ALIAS_INVALID`，同时列出请求值、允许值或目标路径。Tutor 不会搜索、猜测或重复调用，而是说明尚未落盘并返回 Coach 修正 Lesson。

### 5.4 `source_resolve`

解析 learning set 内的相对文件、Markdown 标题锚点和 YAML `#step=<id>`。越界路径、缺失文件和不存在的 fragment 都会明确失败。

### 5.5 Pi 的角色专属写入

Pi Runtime 在四个领域工具之外提供窄写入：

- Roadmap Coach：`roadmap_update` 修改里程碑与尚未物化的 Plan Candidate；
- Roadmap Coach：`plan_prepare` 物化一个学生选中的 Candidate，由 Runtime 分配 Plan
  ID/路径、绑定父节点并生成 `prepared` 文件；
- Plan Coach：`plan_update` 修改当前节点决定与尚未物化的 Lesson Candidate；
  `complete` 必须在同一次写入中封存带来源的 Plan Handoff；
- Plan Coach：`lesson_prepare` 物化或重新准备一个 Candidate，由 Runtime 分配
  Lesson ID/路径、编译 Block/alias，并原子更新 `Lesson Tree`；
- Plan Coach：completed Plan 的 `memory_review_propose` 只保存候选；学生提交后，
  Runtime 校验 review ID 和来源并以可回滚的双文件操作写入两份规范画像；
- Tutor：`classroom_update` 推进 Block、记录路线变化或暂停；
- Tutor：`lesson_close` 在学生确认后写入 Lesson Summary、closed 状态和 Handoff；
  合法 Claim 无法形成时自动使用 source-only Handoff，不阻塞关课；
- Tutor：`card_alternative_append` 把已验证的真正另解作为独立条目旁挂到题卡，并以当前 correct active Trace 作为来源。

这些不是新的公共 MCP API。每个工具只操作当前 `studyforge.session-owner.v2`
绑定的节点；三类 Agent 都没有面向整个 learning set 的 generic write/edit。
Plan/Lesson 的激活和长期记忆应用是 Runtime-only 动作，不暴露给模型。只有成功回执
返回后，Agent 才能宣布物化、写入或结课完成。

## 6. 题卡、知识图谱与方法聚合

题卡保存目标、参考主方法、参考次方法、结构、稳定解题步骤和必要的教学提示。知识图谱使用容易理解的目标、方法和题型分类，不把大量任意前置关系塞进全局图。

Trace 是题卡关系的唯一 owner：

```text
Trace -- cardPath / cardStepId --> Card
Card  -- 请求内按 cardPath 反向聚合 --> Trace[]
```

### 6.1 实际方法证据

题卡声明的方法只说明参考解怎样组织，不能证明学生本次使用了什么。Tutor 先用普通语言描述学生的决定性路线，再询问某个规范节点是否贴切：

- 学生明确确认后，Trace 才记录 `primary`/`secondary` 方法；
- 学生拒绝、希望自己命名、认为没有贴切节点或暂不决定时，Trace 保持 `unmapped`；
- 学生后来改变选择时，追加 superseding Trace，不改写旧记录；
- “最接近”的合法名称仍可能是假证据，不能强行绑定。

正确性、帮助来源和方法归属彼此独立。一个答案可以正确但方法未映射，也可以正确且实际依赖 Tutor。

### 6.2 方法聚合与能力图

聚合先按一次真实作答折叠 Trace：

```text
lessonPath + blockId + cardPath
```

同一题同一 Block 的多条 step Trace 最多贡献一次 attempt。Pi 中一个 problem Block 只保留一条 active 修订链；公共 MCP 仍可为同一次作答记录多个题卡步骤。多问题卡逐问作答时由不同 `blockId` 分开，所以各问的方法和来源不会串在一起；它们仍共享同一个 `cardPath`，不会伪装成多张独立题卡。Trace 的主方法权重 2、次方法权重 1，再结合 assessment 与实际 support；同一 attempt 内的多条 Trace 先按现有规则取平均。只有另解的来源 Trace 仍 active 时，学生确认的另解方法才以自身 support 作为该 attempt 的一条主方法贡献；同一方法在同一 attempt 中只保留系数最高的一条。`steady` 至少要求分数达到当前阈值，并来自两张不同题卡，不能由一张题的多个步骤、小问或多个另解堆出来。

这个结果会生成 `planner-attention.md` 和 Pi 右侧能力节点，帮助 Coach 决定下节课关注什么。它不是科学校准的掌握概率，也不能自动完成 Plan。

### 6.3 真正另解

只有某一整题或某一问存在一条完整路线，并且它的入口、决定性推理和收束链条与参考解及已有另解都真正不同，才算另解。

以下情况不算另解：

- 只换记号或调整等价步骤顺序；
- 把同一条链拆成更多步骤；
- 只替换一个局部计算技巧；
- 只给同一路线换了方法名称。

Tutor 必须先写正确的 active Trace，再判断另解自己的方法归属。Tutor 用普通语言提出至多一个规范节点并询问学生是否贴切：确认后传入该节点；学生否定、暂缓或没有精确节点时传 `null`。写入工具同时记录这条路线实际依赖的 support，并用 `question` 标识另解范围：无小问题卡规范化为“整题”，多问题卡只接受实际不同的那一问。

每次成功写入都会在题卡旁的 Markdown sidecar 新增独立 `alt-NNN`，保存题问、完整路线、方法或未归类值、support 和来源 Trace。来源 Trace 后来被 supersede 时，sidecar 条目不会隐藏或删除，仍可用于审计和检索；但它的方法会退出当前能力投影。明确更正或删除另解时，直接按 ID 编辑对应 Markdown 章节，再运行现有 Planner Attention rebuild。

## 7. 标准学习闭环

1. 学生和 Coach 讨论并确认 Roadmap、当前 Plan 和下一步方向；第一个 Plan 建立前先写回并重读 Roadmap 的 Goal、Observable Capability Standard、Test。
2. Roadmap 先增加 Plan Candidate；学生选择后 `plan_prepare` 才物化完整 Plan，学生再次点击才激活独立 Coach Session。
3. Plan Coach 读取父节点冻结交接和已有子 Handoff，先增加 Lesson Candidate，再按需加载备课 Skill、检索真实题卡并用 `lesson_prepare` 只物化近期课堂。
4. prepared Lesson 只显示无剧透就绪信息。学生点击开始后，Pi 校验父子关系、Activation Snapshot、Block 和 alias，通过后才原子激活并创建/恢复独立 Tutor Session；Claude Code 入口则加载课堂 Skill。
5. Tutor 每次只推进当前 Student View。学生提出暂停、继续思考或结束时，优先服从该选择。
6. 一次有证据的学生作答先写 Trace，再提供学生明确请求的提示。后续补全必须 supersede 同一 attempt 的 active Trace。
7. Tutor 在评价前冻结学生已经亲自给出的内容；缺少决定性证明时写 `incomplete`，不能用 Tutor 自己补出的步骤把它升级为 `correct`。
8. 正确后完成必要的 Trace 写入并明确确认；Trace 方法和另解自己的方法节点都可由学生确认、拒绝或暂缓。真正另解在 Pi 中以独立 ID 持久化并索引回来源 Trace。之后按学生意图继续，不自动倾倒标准解。
9. 达到本课第一条能力标准后，Tutor 可以邀请学生提建议，但是否继续、暂停或结束仍由学生决定。
10. 学生确认结束后，Tutor 停止新的教学和复盘问题，从 active Trace、直接来源、已完成内容、证据缺口和真实停止点写 Lesson Summary 与 Handoff；Claim 无法成立时使用 source-only Handoff。只有 `lesson_close` 成功回执返回后才宣布关闭，任何 Block 都不会被关课动作补成 completed。
11. Pi 保留原 Tutor Session 的只读 Replay。学生明确返回学习顾问后，Coach 先读 Lesson Handoff；只有必要时才下钻原始 Trace、Block、题卡或 Session，再据此调整尚未物化的 sibling。
12. Plan 第一次准备完成判定前，即使深度模式关闭，也先运行一次只读 Quick Evidence Scout 核对拟定结论、边界和来源。Coach 吸收结果后在一次 `plan_update` 中写 Plan Summary、completed 状态和 Plan Handoff；只有证据达标且学生明确选择完成，才进入长期记忆汇总。
13. Plan 完成后，Pi 展示其他 Roadmap Plan，但保持当前页面不变；学生点击某个 Plan 后才进入它独立的 Coach Session。若学生选择重开当前 Plan，则先显式 replan，再继续备课。

### 7.1 学生证据、提示与评价

`assessment` 表示数学完成度，`support` 表示最终答案实际依赖的帮助来源：

- 学生自己的决定性链条完整：可以写 `correct`；
- 已有步骤正确但缺决定性证明：写 `incomplete`；
- 学生自己的链条含实质错误但仍有可保留部分：写 `partially_correct`；
- Tutor 曾给提示但最终没有采用其中的新决定性内容：仍可写 `support:none`；
- 最终解答采用了 Tutor 首次给出的关键方法、比较对象、变形、中间式或结论：写 `support:tutor`；
- 只有真实课堂中无法从内容判断方向性提示是否起作用时，才中性询问学生，不为了覆盖测试而固定追问。

“看过提示”和“依赖提示”不是一回事。原始 Session 保存提示暴露事实，Trace 的 `support` 只服务于最终证据归因。

### 7.2 正确路线后的控制权

学生给出非参考路线时，Tutor 必须先重建完整推理并逐项验证。如果路线正确，完成必要的证据写入后明确确认，并按学生意图继续当前题、比较方法、进入下一 Block、暂停或结束。除非学生明确请求，否则不主动比较标准方法、给更多提示或展示完整参考解。

## 8. Plan 级长期记忆更新

一个 Plan 完成并封存 Handoff、由 Coach 重读后，Coach 先读取 Plan Handoff 和当前
两份画像。只有某项长期偏好确实依赖课堂细节时，才沿 Claim 下钻对应 Lesson
Handoff、active Trace、Session 或原始材料，然后生成 `add / revise / delete`
候选差量。能力结论、一次作答状态和 Planner Attention 不进入这份候选。

Pi 会把候选作为一张结构化卡片放在对应 Coach 回复之后。每项候选都显示直接来源、
理由、反例和适用范围，并且默认不选择。学生可以逐项采用、改写后采用或不采用，
也可以先点“稍后处理”；卡片仍保留在原 Plan Coach 的聊天记录里，刷新和重启后
可以继续。

状态依次是 proposed、submitted、applied。proposed 表示等待学生逐项确认；
submitted 只表示决定已经保存，不表示画像已经更新。Runtime 校验 review ID、Plan
Handoff 来源和当前 profile 后，原子写回两份画像并保存 receipt；只有这一步成功，
状态才成为 applied，界面才显示“已写入长期画像”及写入/未更改数量。

模型没有记忆应用工具，也不能通用编辑画像。Runtime 只应用采用或改写后的条目，
分配稳定 `S*` / `T*` ID，并把每条长期偏好规范化为
Content、Scope、Sources、Rationale、Counter-evidence。两份文件要么一起更新，要么
失败时一起恢复原状。Coach 随后重读 `student-profile.md` 和
`teaching-profile.md`，再从重读结果报告；前端从不直接编辑画像。

Lesson 关闭、Task 完成、一次正确答题、方法聚合分数或模型推断都不能绕过这道门。

## 9. 日常使用

统一入口：

```text
/highschool-study:study
```

常见自然语言请求：

```text
读取当前学习集，告诉我学到哪里，再和我讨论下一节课。
```

```text
为当前 Plan 备下一课。只使用真实题卡；找不到合适卡就停止找卡。
```

```text
开始这节课。课堂步骤可以根据我的回答重排，我决定何时暂停或结束。
```

```text
查看进度，把能力证据、Plan/Lesson 状态、方法提醒和长期偏好分开说明，并给出处。
```

可以直接调用的辅助 Skill：

- `/highschool-study:inspect-progress`
- `/highschool-study:prepare-next-lesson`
- `/highschool-study:run-lesson`
- `/highschool-study:close-lesson-reflection`
- `/highschool-study:correct-learning-record`
- `/highschool-study:consolidate-plan-memory`

通常不需要手动切换 Agent；`study-coach` 会在统一入口内部路由备课和上课。

### 9.1 Pi 前端日常流程

在 Pi 中运行 `/study-web` 后：

前端有三个平级主视图。它们不是三个学习数据库，而是同一份事实的三种观察坐标：

| 主视图 | 学生用它做什么 | 事实来源 |
| --- | --- | --- |
| **课程脉络** | 看 Roadmap → Plan → Lesson 的组织关系，继续学习、开始课堂、回顾或重新备课 | Roadmap、Plan、Lesson 和 owner 匹配 Session |
| **知识山河** | 看正式方法树、题卡与材料，以及自己在哪些方法上留下过有效课堂记录 | `graph/`、公开题卡/材料 metadata、active Trace |
| **研习留痕** | 看已确认偏好、阶段认识、未决问题和原始来源，并沿证据树回到课堂 | profile、Handoff Claim、Trace、Block、Session、Card |

`/course` 是默认入口。“课程脉络”直接展开 Roadmap → Plan → Lesson，并按
`active → paused → prepared → Plan Coach` 计算唯一续学位置；没有未完成 Plan
时进入 Roadmap Coach。Candidate 只表示父节点仍在商议的可能下一步，没有文件、
Session 或开始按钮。prepared 节点只有学生明确点击才激活；active/paused 节点继续
原 Session；closed/abandoned 节点只读回放。

Plan 页面保留该 Plan 的 Coach 对话和真实 Lesson 子 Session。只有已经激活且 owner
完全匹配的 Lesson 才进入 Session 历史；prepared Lesson 只显示无剧透目的、课堂
形态、环节数量和真实资料编号。真实课堂位于
`/course/plan/<plan-id>/lesson/<lesson-id>` 专注子页面：唯一 active Block 的
Student View 与已揭示题卡进入对话，课堂节点列显示真实进度。离开它去知识山河或
研习留痕只会改变观察页面，不会暂停、关闭、重建 Tutor Session，也不会复制聊天。
课堂中仍可上传 PNG、JPEG 或 WebP 草稿；学生明确暂停、继续、结束或返回 Coach
时，才执行相应课堂动作。

“知识山河”的底图只来自学习集正式 Method Tree。题卡的 `primary` 与 `secondary`
仍是“题卡怎样连接到方法”的边角色，不会把自由 `subroute` 或卡片文字升级成新
知识节点。学生个人状态只是覆盖在底图上的 active Trace 信号，使用“未观察”“已有
记录”“在不同题卡上更稳定”“历史记录已失效”等文字，并显示独立题卡数量；它不
展示分数、百分比或自动 mastery 结论。prepared assessment、未揭示 Block、
Teacher Control、答案和私有选卡理由不会因为切到知识页而泄露。窄屏不把整棵图
压成缩略图，而改用保持父子层级的文字方法列表。

“研习留痕”把五类内容分开：

- **已确认记忆**：学生逐条确认后写入的长期学习或教学偏好；
- **阶段认识**：Plan/Lesson Handoff 中有边界、有来源的当前判断；
- **还要再看**：尚不能下结论的问题与下次核验方式；
- **仅有来源记录**：source-only Handoff，只保留真实 Source Index，不伪造 Claim；
- **已失效历史**：来源被 supersede 后保留用于回看，但不参与当前判断。

每项判断都能沿 Handoff → Trace / Session / Card / Block 回到原始信息。点击“提出
异议”只会打开拥有该判断的 Coach，并把来源与异议草稿预填到输入框；它不会自动
发送，也不会更改任何事实。只有学生发送、Coach 复核、作用域工具成功返回回执后，
页面才可以说记录已经更正。

三个主视图共享 Plan、Lesson、方法、题卡和来源选择坐标。浏览器地址只保存这些
定位值，不保存模型生成内容，也不能扩大当前节点、Session 或来源权限。刷新、后退、
前进或直接打开合法深链时，App Shell 始终保留，前端重新读取只读投影并恢复
owner 匹配的 Coach、active Tutor 或 closed Replay；不会隐式激活或切换节点。每次
返回课程根页都会重读 Roadmap，因此刚物化的 Plan/Lesson 会立即出现。

中等宽度把节点详情移到主内容下方，窄屏按“主导航 → 当前节点 → 对话/内容 → 详情”
顺序纵向展开；状态始终有文字而不只依靠颜色。系统要求减少动态效果时，跨页和课堂
导航仍可正常使用。

重新备课分两种：

- Lesson 仍是 `prepared`：Coach 保持 Lesson ID 不变，学生确认方向后原地修改；
- Tutor 已经开始：旧 Lesson 标记为 `abandoned` 并保留，Coach 创建新的替代 Lesson。

### 9.2 Learning Set Overview、研习要领与陪伴风格

没有课堂 Trace 时，`study` 会展示 `ROADMAP.md` 的 Learning Set Overview；已有 Trace 时，只有学生要求才展开这份概述。

如果存在 `LEARNING_GUIDE.md`，Claude 入口与 Pi 首页只展示其中的 `Student Learning Principles`；内部教研笔记保持在备课/授课私有上下文。

学习集可以在 `.claude/personas/<id>.md` 添加专属人设，或用同名文件覆盖内置人设。面向学生的公开元数据使用 `ID`、`Display name`、`Student preview`、`Glyph`、`Accent` 和可选 `Portrait`；抽屉只读取这些字段，不显示内部提示正文。Portrait 必须是 learning set 内真实存在的 PNG、JPEG 或 WebP。临时人设选择不写文件；持久选择写入 Git 忽略的 `CLAUDE.local.md`。人设只改变面向学生的表达，绝不改变能力判断、题卡、Trace、能力标准或备课。

Pi 允许 Coach/Tutor Session 各自选择陪伴风格；选择只写入该 Pi Session 的 custom entry，不复制到其他 Session。柔和动效和完成反馈则只保存在当前浏览器的 `studyforge.presentation.v1`，不会进入 Session、learning set 或模型上下文；系统要求减少动态效果时始终优先关闭动效。

### 9.3 自适应课堂与防剧透

备课会根据当前目标和 Trace 选择一个主模板：诊断课、概念新授课、专项训练课、错因修复课、能力验收课或复习整合课。模板只是 ActivityBlock 的默认组合，学生仍可增删、跳过和重排。

Planner 先确定热身、核心、变式、迁移、补救或挑战等题目角色，再分别搜索真实题卡；不会找到第一题就停止。真实卡片不足时会缩减题组或调整课堂目标，不会临时编卡。

题目 Block 分为 `Student View` 与 `Teacher Control`。Coach 只展示当前 Student View，并按三种模式揭示：`zero` 在诊断和验收首次尝试前不给提示；`ladder` 在学生尝试并同意后每轮只给一级提示；`worked-example` 可以完整讲示例，但学生目标题必须是另一张真实卡。Teacher Control、题卡答案和解法步骤不会被整段转述给学生。

视频优先使用本地 `materials/`。外部视频只有在备课侧核验真实标题、链接、相关片段、教学目的和文字替代后才会加入；解决目标题的视频不会放在首次尝试之前。

### 9.4 结构化事件与安全投影

Pi 前端不会把底层工具调用直接渲染成消息瀑布：

- 默认 `safe` 模式只显示完成的纯文本消息；
- 含工具调用的混合消息投影为“正在搜索题卡”“正在记录证据”等结构化状态；
- Roadmap Coach 私下检索后，safe 模式不会显示模型对题卡的自由总结；Plan Candidate
  与 prepared Plan 只投影公开目的、依赖和学生可执行动作；
- `lesson_prepare` 成功后，safe 模式重新读取已经落盘的 Lesson，并把紧随其后的 Coach 自由 final 替换成课程就绪卡；首页、学习情境与历史恢复使用同一只读投影。它只投影真实进度、模板安全的学习目的、环节数量与活动类型，以及题卡真实 `content_item_id` 短号，不投影真实课题、题面、方法、选卡理由、路径、Teacher Control 或 pending Student View；
- 安全字段缺失时只省略可选信息或显示通用说明，绝不回退到 private note、Teacher
  Control、active Plan Summary 或文件名猜测；完整 Plan/Lesson Markdown、Authoring
  source、Pi JSONL 和 `raw-stream` 仍保留给 Coach 与本地审计；
- 工具参数、私有证据矩阵、Teacher Control 和子任务结论不进入 Student View；
- 原始 Pi JSONL 始终完整保留，便于本地审计；
- `raw-stream` 仅用于开发诊断，可能显示混合工具文本、工具参数和私有过程，不应
  作为学生默认模式；三个主视图及其只读接口始终使用 student-safe 投影，不因展示
  模式切换而把 Teacher Control 或未揭示资产加入公开 view contract。

四块界面没有另建学习状态：

- 课程脉络、知识山河、研习留痕、专注课堂、课堂情境和研习资料都从
  Markdown/YAML、active Trace 与当前 Session 重建；三个
  `GET /api/views/{course,knowledge,memory}` 接口只读，学生投影不落盘，也不取代
  Coach 对原始 Plan 的完整读取；
- 课堂本仍保存初始节点和当前节点，路线的 insert、skip、move、repeat 仍以来源和理由追加；
- 研习资料只返回当前 Session 权限内的学生安全预览，并让题卡与完整 active Trace 双向联查；无命中时明确为空，不编造资产；
- 陪伴风格选择属于当前 Pi Session，柔和动效和完成反馈仅属于浏览器本地展示状态；
- overlay 关闭后保留原 Session、路由和页面滚动，不创建新的学习事实。

关闭后的 Replay 聚合真实消息、结课时 Lesson Summary、Trace、路线变化和图片；关课时仍为 active 的 Block 保留为真实停止位置，不会伪装成已完成。若原 Pi 历史不可用，则明确降级为 evidence-only，而不是伪造对话。

能力图在成功追加 Trace 或题卡另解后主动发布一份完整 snapshot。点击方法节点可以通过证据透镜回到当前作为能力来源的 active Trace 和安全题卡 metadata。已经 supersede 的 Trace 仍能从 sidecar 审计其历史另解，但不再作为当前方法节点来源。能力图展示的是当前方法信号，不是自动 mastery 判决。

### 9.5 深度模式与动态工作流

深度模式按 Coach/Tutor Session 单独开启，默认关闭。信息足够时仍直接回答。

Plan 第一次准备判定 `complete` 是唯一例外：即使开关关闭，Plan Coach 也保留一次
单任务 Quick Evidence Scout。它使用 50,000 token、最多 180 秒，只检查拟定
conclusion、boundary、关键/辅助来源中的冲突、遗漏、支持条件、旧表述和无法重读的
写入，不给出完成与否的裁决。Coach 仍是决定者；Scout 失败或超时时要收窄 boundary
并留下 open question，而不是静默通过。

- `quick`：最多三个无依赖任务、最长 180 秒，可直接运行；Token 总预算由父 Agent 声明，单个 Plan 级 Evidence Scout 约定使用 50,000；
- `deep`：允许依赖波；运行前在任务轨展示目标、并发、Token 和时间预算，由学生确认；
- proposed/running 工作流可以取消；已完成分支保留，未完成分支不会自动重试；
- 状态保存在父 Pi Session JSONL 的 custom entries；
- 任务轨运行中只显示安全化活动名、耗时、Token 和工具次数，完成后才汇总题卡数与来源数；不会投影子任务参数、思考或半成品输出；
- Evidence Scout 只接收证据问题和范围，父 Agent 不先批量读取同一 Plan；子任务没有学习状态写权限，父 Agent 负责核验来源并决定是否采用。

服务重启时，先前的 running 工作流恢复为 partial 或 failed 终态，不会悄悄续跑。

## 10. 更正记录

若发现某条课堂事实记错，不要编辑旧 Trace。可以说：

```text
更正 lesson-002 的 event-001：定义域是独立写出的，但同构变形用了两步提示。
保留旧记录，用 Supersedes 追加更正并刷新派生证据投影；列出可能过时的摘要或决定，但不要自动改写。
```

学生对评价提出异议时，Tutor 先重新检查学生原始路线。若接受异议，必须在后续课堂总结或进度讨论之前先追加 superseding Trace。方法节点同样如此：只有 active Trace 已绑定不贴切节点时才追加 superseding Trace，更正为未映射或学生确认的替代节点；若本来就没有方法绑定，则保持 `unmapped`，不制造虚假的纠错事件。

普通题卡搜索和 Trace 搜索只把 active Trace 当作当前课堂观察；能力投影与 Planner Attention 也只纳入来源仍 active 的 Trace 方法和另解方法。Trace 更正会刷新这些派生投影，但不会自动重写已经落盘的 Lesson Summary、Plan 决定、另解 sidecar 或已确认画像；系统只报告哪些内容可能已经过时。另解条目本身有误时，按其 ID 明确编辑或删除旁挂章节，再重建 Planner Attention。

如果更正影响已经确认的长期偏好，插件不会静默修改画像；它会在下一次 Plan 级压缩时把修改或删除重新交给学生确认。

## 11. 创建自己的学习集

复制插件模板：

```bash
cp -R /path/to/highschool-study/plugins/highschool-study/learning-set-template ./learning-set
```

然后进入项目运行 Claude Code，并说：

```text
/highschool-study:study
和我一起制定 Roadmap。先讨论目标，再把可观察能力标准和测试写在文档末尾。
```

题卡可以逐步加入 `learning-set/cards/`；Lesson 里的别名必须映射到真实相对路径。资料放进 `materials/` 后，用相对链接引用。

## 12. 排错

### `/plugin` 不存在

运行 `claude --version`，更新 Claude Code 后重启终端。

### 插件已安装但 MCP disconnected

先运行：

```bash
bun --version
claude mcp list
```

确认 Bun 在 `PATH` 中，并确认启动 Claude Code 的项目根目录下存在 `learning-set/`。

### `card_search` 返回空数组

这是正常的真实性 fence。检查 `learning-set/cards/` 是否有真实题卡，或调整搜索词。不要要求模型凭空补一张卡；需要新题时，应先以明确流程制作并审查题卡。

### 安装了新版本但会话仍是旧行为

更新 marketplace 后运行 `/reload-plugins`，或退出当前 Claude Code 会话再重开。

### 示例中的教材来源解析失败

公开试用集不分发教材原图和整书原文。题卡步骤、Lesson、Trace 和学习状态仍然可用；若需要核对外部教材页，请在自己的 learning set 中放入依法持有的材料，并修正题卡中的相对来源路径。

## 13. 开发者验证

Claude Code 插件：

```bash
cd plugins/highschool-study
bun install --frozen-lockfile
bun run release:check
```

发布检查包含 MCP bundle、TypeScript 类型检查、自动测试和 Claude Code 严格插件验证。插件公共工具面必须始终只有 `card_search`、`trace_search`、`trace_append`、`source_resolve`。

Pi 教学前端：

```bash
cd apps/pi-teaching-web
bun install --frozen-lockfile
bun run check
bun run test:e2e
```

`check` 包含 TypeScript、非 E2E 测试和生产构建。涉及浏览器路由、Replay、能力刷新、Student View 或事件投影时还必须运行 Playwright。当前集成用例还会把续学首页、固定课堂、课堂情境、研习资料、陪伴风格、暂停恢复和回放路由串成一次完整验收。

真实模型验收必须复制导数学习集到 `/tmp` 或其他隔离目录；不要让验收 Session 修改仓库中的公开示例。Provider 凭据和 Pi Session JSONL 不得提交。

教学 Prompt 变更的最终验收使用配对 A/B 真课：旧版与新版保持同一 Provider、模型、干净学习集起点、学生设定和课堂目标，先隐藏版本身份，再比较目标选择、任务关系、学生路线理解、介入时机、迁移证据和课堂自然度。工具调用成功只是进入质量比较的前提。若两组配对不能显示一致、可定位到具体回合的改善，结论应写 `INCONCLUSIVE`，不能把自动测试通过当作教学质量提升。

## 14. 明确不做的事情

当前版本不包含：

- SQLite、向量数据库和后台索引服务；
- 自动统一编译整套上下文的 `study_context_get`；
- 以 Lesson 或 Task 完成为依据自动写长期画像；
- 人类教师介入与班级管理；
- 自动把 learning set 提交到 Git；
- 为极低概率边角情况堆叠的产品化防御层。

它的定位仍是一套可读、可审计的本地学习插件与教学前端，不是包含账号、云同步、班级管理和商业运维能力的完整教育 SaaS。
