# Tutor Block 进入与帮助触发小修设计

## 背景

M0 真实课堂已经跑通 Roadmap → Plan → Lesson。第一题暴露了两个彼此独立、但都属于
Tutor 执行契约的毛刺：

1. Tutor 在聊天和 `Classroom Log` 中声称首个 Block 已激活，却没有在呈现题目前把
   `Node State / Status` 从 `pending` 写成 `active`。完成第一题时状态才恢复正确。
2. 学生明确约定“没说卡住之前不要提示”，随后只表达“还没想清楚”。Tutor 把这种
   未完成思考当成求助，主动给出了归组公式和母函数方向。

两处都发生在模型如何执行现有 Lesson 文档上。Runtime 已正确处理 Lesson 生命周期、
Session 恢复和 Markdown 解析；不需要新增状态机、工具、投影或持久化字段。

## 设计决定

只修改 `tutor-lesson/SKILL.md`，把两个模糊动词改成可观察的执行契约。

### 1. Block 进入顺序

当 Lesson 没有 active Block 时，Tutor 必须按以下顺序进入第一个合适的 pending Block：

```text
read Lesson 与 Uses
→ edit：只把当前 Block 的 pending 改为 active
→ read Lesson，确认状态已经落盘
→ 呈现 Student View
```

激活编辑不与 `Classroom Log` 追加合并，避免为了匹配空日志而跨过下一个 Block 标题。
第一次有意义交流后再按原规则追加日志。日志里写“已激活”不能替代 `Node State` 的真实
状态。已有 active Block 时继续该 Block，不得同时激活第二个。

### 2. 帮助触发条件

每个 Block 可以与学生约定帮助触发方式。只要约定里存在可观察的触发条件，例如学生
明确说“卡住了”或直接请求提示，Tutor 就按这个条件判断：

- “我还没想清楚”“我正在想”“这里有点犹豫”只表示思考未结束，不等于请求帮助；
- 触发前可以复述、核对或评价学生已经说出的内容，但不能补充新等式、新变形、新方法名、
  新目标关系或决定路线的问题；
- Tutor 若不确定学生想继续独立思考还是要提示，只问这一个选择；
- 学生明确请求评价某一步时，可以判断该步是否成立，但不借评价继续推进未请求的后续解法；
- 触发后才按原有“方向 → 关系或一步 → 完整讲解”的渐进原则提供帮助。

没有特殊约定的 Block 继续使用现有的一般帮助原则。本设计不把“卡住”硬编码成全局唯一
口令，而是要求 Tutor 遵守当前课堂已经确认的学生边界。

## 验证

仓库约定不为 Skill 自然语言写逐字断言。验证分三层：

1. 现有装配与文档契约测试继续通过；
2. 新建独立 Lesson Session，第一题呈现前检查 Block 已是 `active`；
3. 用与基线相同的学生表达“还没想清楚”，检查 Tutor 只确认已有判断或询问是否要提示，
   不再主动给出归组公式与母函数方向。

通过后再继续一轮节点推进，确认 `completed → next active` 和刷新恢复没有回归。
